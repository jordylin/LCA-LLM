## 是否可以加入更小的模型？

可以，该框架支持加入额外的小型模型进行对比，但有一些注意事项。

### 为什么可行

服务层已经是模型可替换的：

- [start_vllm.sh](/home/Research_work/24_yzlin/LCA-LLM/start_vllm.sh) 启动一个 vLLM 的 OpenAI 兼容服务
- [backend/app.py](/home/Research_work/24_yzlin/LCA-LLM/backend/app.py) 读取 `VLLM_MODEL_NAME`
- [backend/services/qwen_agent_service_v2.py](/home/Research_work/24_yzlin/LCA-LLM/backend/services/qwen_agent_service_v2.py) 通过 vLLM API 与模型交互

因此，如果某个小型模型可以被 vLLM 服务化，并且能够产生足够稳定的结构化工具调用，它就可以作为一个新的评估目标接入。

### 重要限制

当前的 `lca_lora` 适配器与 `Qwen3-8B` 基础模型系列绑定。它不能简单地复用到不相关的架构上。

因此，存在两种不同的实验类型：

1. `Base-model comparison` （基础模型对比）
   - 对比 `Qwen3-8B base` 与更小的基础模型
   - 无需额外训练

2. `Fine-tuned comparison` （微调模型对比）
   - 对比 `Qwen3-8B + LoRA` 与 `小模型 + 其自身的 LoRA`
   - 需要为每个候选基础模型单独进行微调

## 推荐的对比目标

如果目标是扩展基线家族以包含更小模型，最稳妥的第一步是选用那些更可能配合 tool-calling 风格提示的指令微调模型。

合理的候选类别：

1. 更小的 Qwen Instruct 模型
2. 更小的 Llama Instruct 模型
3. 紧凑的多语言或面向 agent 的 instruct 模型，但前提是它们已表现出稳定的 JSON 行为

这里的关键标准不仅仅是基准质量，而是：

1. tool-call 格式的稳定性
2. JSON 有效比率
3. 无需大幅重写即可遵循现有系统提示的能力

对于该框架而言，一个语义质量稍低但结构化输出稳定的小模型，通常比一个更强但 tool-calling 行为脆弱的模型更有用。

## 建议的后续步骤

### 开展新对比前的最低限度清理

1. 决定哪一份微调结果文件是权威版本。
2. 还原或重写缺失的推理循环脚本。
3. 还原或重写基线指标脚本，使所有模型使用同一套指标实现。
4. 将每次运行的结果保存在按模型命名的目录下，而非重复使用 `predictions_final.json`。

### 多模型评估的最佳路径

1. 添加一个统一的评估运行器，接受：
   - 模型标签
   - vLLM 模型路径
   - 服务模型名称
   - 输出目录
2. 将结果保存为：
   - `results/<model_name>/predictions.json`
   - `results/<model_name>/metrics.json`
3. 使用一个统一的汇总表格对比所有模型。

### 建议的实验阶梯

1. 重新确认 `Qwen3-8B base`
2. 重新确认 `Qwen3-8B + LoRA`
3. 增加一个较小的基础模型
4. 增加第二个较小的基础模型
5. 仅在此之后再决定是否值得为小模型进行 LoRA 训练

## 结论

仓库清楚地表明已经完成了 Baseline 与 LoRA 的对比，并且指标集是可以恢复的。

该对比至少使用了以下七个指标：

1. `Field-level EM`
2. `Numerical Accuracy`
3. `Grounding Accuracy`
4. `Recall`
5. `Precision`
6. `F1 Score`
7. `Valid JSON Rate`

在当前架构中，加入更小的模型在技术上是可行的，特别是通过 vLLM 作为新的基线接入。

主要阻碍并非模型服务化。主要阻碍在于历史评估流程仅被部分保留，在扩展对比集之前需要先统一。
